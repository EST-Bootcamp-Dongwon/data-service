## 0. 이 문서에 대하여

### 0.1 왜 Minor(+0.1)가 아니라 Major(+1.0)인가

v1.0 은 **설계 확정, 구현 대기** 상태의 문서였다. M1~M7 을 지나며 코드가 문서를 크게 앞질렀고, 그 사이 마스터인덱스 §5 에 변경 노트 **N1~N82** 가 쌓였다. 이번 개정이 Major 인 이유는 뼈대 네 개가 동시에 움직였기 때문이다. ① **계약 스키마가 늘었다** — Context Pack 에 `CX_workstream` 블록이 붙고(N36), 단계 응답에 `ledger` 필드가 실리며(N38), 장부의 D- 가 `직접근거`와 `계산유래` 두 갈래로 갈라졌다(N74·N75). "GIC 공통계약을 필드명 그대로 옮긴다"는 §5.2·§5.3 의 전제 자체가 이동했으므로 하위 호환 문서로 볼 수 없다. ② **명세가 스스로 내건 차별점 문장이 실측에 뒤집혔다** — §7.2·§7.4 의 "리포트의 **모든** 수치가 클릭 가능한 근거 링크다"는 실측 연결률 앞에서 성립하지 않는다(N67). M7 에서 파생값을 장부에 올려 14%→43%(CORP-R)까지 끌어올렸지만 여전히 "모든"이 아니다. 이건 표현 수정이 아니라 **제품 약속의 축소**다. ③ **절이 새로 늘었다** — §4.0 가격 소스 · §4.5 조회 구간 · §5.4.1 피어·산업 선정 · §5.7 평가 루브릭 · §5.8 장부 규칙 · §5.9 표기 규칙 · §6.4 차트 API · §6.5 시장 분석 API · §6.6 데이터 실험실 API · §8.2 배포용 축약본 · §10 회귀검사. 기존 절 수정이 아니라 목차가 늘어난다. ④ **계층 규칙이 바뀌었다** — 저장소가 `원본 → 축약본 → 라이브` 3단으로 갈라지고(N23), 지연 로딩 잠금 규칙이 생겼으며(N57), `core/parallel.py` 로 동시 호출 계층이 추가됐다(N59). 여기에 화면 셋(`/market` · `/timeseries` · `/research`)이 늘어 IA 가 재편됐고(N18·N26·N62), 데이터 소스 둘(HuggingFace · 금융감독원)과 배포 데이터 넷이 더해졌다.

## 1. 시스템 아키텍처

### 1.1 계층 규칙

기존 규칙을 그대로 지킨다. **아래 계층은 위 계층을 import 하지 않는다.**

```
routers/      ← DTO · 엔드포인트 (얇게)
services/     ← 계산 · 판단 (여기에 로직이 모인다)
repositories/ ← 저장 · 캐시
clients/      ← 외부 HTTP 연동 · 응답 정규화
core/         ← 순수 유틸 (아무것도 import 하지 않는다)
```

M2~M5 를 지나며 여기에 규칙 셋이 더 붙었다.

**① 저장소는 원본이 비면 갈라진다** (N23)

`krx_store` 의 조회 함수는 원본 캐시(`krx_cache.db`)가 비어 있으면 축약본(`krx_bundle.db`)으로 넘어가고, 그것도 없으면 라이브 호출로 간다. **서비스·라우터를 한 줄도 고치지 않고** 배포본을 살리려면 갈라지는 자리가 저장소 계층이어야 한다.

```python
# app/repositories/krx_store.py:271
def source() -> str:
    """지금 어느 데이터를 보고 있는지 — `cache`(원본) · `bundle`(축약본) · `live`(둘 다 없음)."""
    if not _cache_is_empty():
        return "cache"
    return "bundle" if krx_bundle.available() else "live"
```

`source()` 가 셋 중 무엇인지 밝히고, 화면 배지와 리포트가 "무엇을 근거로 말하고 있는지"를 그 값으로 적는다.

**② 지연 색인은 잠금 밖에서 `load()` 를 먼저 부른다** (N57)

`threading.Lock` 은 재진입이 안 된다. 잠금을 쥔 채 `load()` 를 부르면 그쪽이 같은 잠금을 다시 잡으려다 멈춘다.

```
배포본 GET /api/research/glossary?term=PER   →  62.7초 타임아웃 (504)
```

로컬에서 안 걸린 이유는 검사할 때 늘 `stats()`(→ `load()`)를 먼저 불러 캐시가 차 있었기 때문이다. **프로세스의 첫 호출이 `lookup()` 일 때만** 터진다. 해당 자리는 `glossary._build_index` · `industry_store._groups` 다.

**③ 서로 무관한 외부 호출은 동시에 부른다** (N59·N60)

`core/parallel.py` 가 그 자리다. 단, **받아 오는 것만** 동시에 한다. 장부(E-/D-/CALC- 번호) 발급은 정해진 순서를 지킨다 — 순서가 흔들리면 같은 종목의 리포트가 실행할 때마다 근거 번호가 달라져 재현되지 않는다 (공통계약 §13 회귀검사).

**② 공시 목록에서 지분공시를 빼는 이유** (N12)

삼성전자 12개월 3,444건 중 지분공시가 **3,271건(95%)** 이라 100건 한도가 노이즈로 다 찬다. 빼니 실적 2→19건 · 자본 0→11건으로 신호가 살아났다.

> v1.0 은 이 항목을 "CORP-TP `H04` 가 쓴다"고 적었으나 **틀렸다** (A7). 공시 목록은 `stages.h02_evidence()` 가 **네 작업 공통으로** 수집해 E- 를 발급한다.

**③ 한 번 호출에 3개년이 온다** (N37)

응답에 `value` · `prev` · `prev2` 가 함께 실린다. 5년치를 5번 부르지 않는다 — **5회 0.7초 → 2회 0.28초.**

**④ 성능 — 로컬 값을 배포 판단에 쓰지 마라** (A6)

| 환경 | 실측 |
|---|---|
| 로컬 | 삼성전자 2024 연결 **0.14~0.17초 · 213계정** |
| **배포본** | **회당 6~7초** (로컬의 10~40배). 동시 호출로 3회를 1회 대기로 줄인 뒤에도 H02 평균 **9.1초** |

**DART 회당 6~7초는 우리가 못 줄인다.** 그래서 진행률 모달이 미리 말하고(§7.3), 끝난 뒤에 어디가 느렸는지 밝힌다(`CX_workstream.h02_timing`).

**⑤ 원문 파싱은 배포본에서 기본 OFF** (N41)

원문(0.8MB ZIP) 내려받기가 서버리스 60초 상한을 넘겨 H02 가 통째로 죽었다. 실측 — 같은 인스턴스에서 H03(재무제표)은 콜드 15.2초·웜 0.32초로 멀쩡한데 **H02 만 두 번 다 60초 타임아웃**. 켜 둔 채로는 앞서 모은 근거까지 전부 날아간다.

- 배포본 기본 OFF, `options.include_report_document` 로 켤 수 있다.
- 로컬 기본 ON.
- 결과 — 기업 계열 리포트가 **로컬 14장 · 배포본 11장**. 산업 계열은 원문을 안 써서 장수가 같다.
- 회사마다 서식이 달라 원문에서도 안 나오는 것이 있다 (신한지주는 부문·점유율·생산능력 전부 없음, 카카오는 점유율 없음) → `G-DATA` 로 밝힌다.

## 3. 전처리 명세

> 기획서 §1 의 "데이터 전처리가 확실해야 시계열 분석이 정확하다"를 구체화한 부분이다.
> **전처리 결과는 그 자체로 `stage_result` 에 실린다.** 이 모듈은 "조용히 고쳐 주는" 일을 하지 않는다 — 고친 것을 전부 세어서 함께 돌려준다.

### 3.1 파이프라인

```
원본 OHLCV
  │
  ├ P1 거래일 정렬     중복 제거 · 날짜 오름차순              calendar.sort_and_dedupe
  ├ P2 결측 처리       연속 3거래일 이하 → ffill               calendar.fill_and_trim
  │                    초과 → 구간 절단 + G-DATA
  ├ P3 이상치 검사     |로그수익률| > 5σ 또는 ±30% → 플래그    quality.find_outliers
  │                    (제거하지 않는다 — §3.3)
  ├ P4 액면·배당 조정  수정주가 사용 여부를 기록               normalize.mark_adjusted
  ├ P5 통화·단위       KRW/USD 명시 · 억/조 환산은 표시 계층만  normalize.normalize_series
  └ P6 품질 리포트     §3.2 표 생성                            quality.build_report
```

**① "연속 결측 3일"은 실제 거래일 기준이다** (N15)

`preprocess.run(trading_days=…)` 으로 그 시장의 **실제 개장일 목록**을 넘길 수 있다. 국내는 `krx_store.available_dates()` 를 그대로 넘긴다. 안 넘기면 주말만 빼는 근사로 떨어진다.

```
캘린더 없이 삼성전자 250거래일 → 추석 연휴(5거래일)를 결측으로 오판
                              → 앞쪽 51행(20%)을 근거 없이 잘라 냈다
캘린더를 주면                 → 250행 전부 보존 · 충실도 100%
```

**② P4 는 소스마다 다르다** (A9)

v1.0 은 "yfinance `auto_adjust=True` 사용"이라고 단일하게 적었으나 실제는 갈라진다.

| 소스 | 설정 | 자리 |
|---|---|---|
| 국내 (KRX) | `auto_adjust=False` | `ts_service.py:140` |
| 해외 (야후) | `auto_adjust=True` | `ts_service.py:193` |

조정 여부는 `adjustment` 로 돌려주고 D- 레코드에 기록한다.

**③ 충실도 분자에서 메운 날을 뺀다**

```python
# app/services/preprocess/quality.py — 메워 넣은 날은 실제 거래일이 아니므로 분자에서 뺀다.
actual = len(clean_rows) - (calendar_report.get("filled_days") or 0)
coverage = round(actual / expected, 4) if expected else 0.0
```

빼지 않으면 **구멍을 메울수록 품질이 좋아지는** 이상한 셈이 된다.

**④ 입력이 비어도 예외를 던지지 않는다.** 빈 결과 + `insufficient` 판정으로 돌려주고 호출한 쪽이 `partial-continue` 로 넘어가게 한다 (불변원칙 §2-2).

**근거 노트**: N15 · A9

### 3.2 품질 리포트 필드

> v1.0 은 8행이었다. 실제 `quality.build_report()` 가 내는 것은 **19필드**다.

| 필드 | 내용 |
|---|---|
| `rows_raw` / `rows_clean` | 처리 전후 행 수 |
| `duplicates_removed` | P1 에서 지운 중복 행 수 |
| `date_first` / `date_last` | 실제 데이터 범위 |
| `expected_trading_days` | 기대 거래일 수 (분모) |
| `missing_days` / `missing_dates` | 결측 거래일 수 · 목록 |
| `filled_days` / `filled_dates` | ffill 로 메운 일수 · 목록 |
| `trimmed_rows` / `trim_reason` | 긴 구멍 때문에 잘라 낸 행 수 · 사유 |
| `outliers` | 이상치 `{count, max_abs_pct, 목록}` |
| `coverage_ratio` | `(rows_clean − filled_days) / expected_trading_days` |
| **`calendar_source`** | `calendar` \| `weekday-approx` — **근사로 셌으면 짧은 결측을 놓칠 수 있다는 한계를 리포트가 밝힌다** (N16) |
| `gaps_emitted` | 발행한 Gap 목록 (코드 · 메시지 · 상세) |
| `verdict` | `usable` \| `usable-with-caveat` \| `insufficient` |
| **`modelable`** | `verdict != "insufficient"` — 라우터·서비스가 이 한 줄만 보고 갈라도 되게 한다 |
| **`limitations`** | 해석 카드의 `limitation` 에 그대로 넣을 **사람이 읽을 문장들** |

판정 경계 — `coverage_ratio < 0.9` 면 `usable-with-caveat`, `< 0.6` 이면 `insufficient` → 시계열 모델링을 건너뛰고 `partial-continue` 로 넘긴다 (불변원칙 §2-2). 관측치가 최소 개수(`MIN_ROWS`) 미만이어도 `insufficient` 다.

`preprocess.summarize()` 는 이 리포트를 한 줄로 줄인다 — `"usable-with-caveat · 248행 · 충실도 96% · 이어붙임 2일 · 이상치 3건"`.

**근거 노트**: N16

### 3.3 이상치를 제거하지 않는 이유

주가의 극단 수익률은 대부분 **진짜 사건**(실적 발표, 유상증자, 급등락)이다. 제거하면 리스크를 과소평가한다. 따라서 **표시만 하고 모델에는 그대로 넣되**, `G-DATA` 를 하나 발행하고 해석 카드의 `limitation` 에 "표본에 ±N% 이상 변동일 M건 포함"을 적는다.

## 4. 시계열 엔진 명세

### 4.0 가격 소스 (신설)

| 대상 | 소스 | 거래 캘린더 |
|---|---|---|

### 4.2 ADF 임계값

`scipy` 없이 구현하므로 MacKinnon(1994) 응답표면 계수를 상수로 둔다. 상수 검정(constant only) 기준이고 **표본 크기 보정항까지** 넣는다.

```python
# app/services/timeseries/stationarity.py:46
MACKINNON_CONSTANT = {
    "1%":  (-3.43035, -6.5393, -16.786, -79.433),
    "5%":  (-2.86154, -2.8903,  -4.234, -40.040),
    "10%": (-2.56677, -1.5384,  -2.809,   0.000),
}
# 임계값 = β∞ + β₁/n + β₂/n² + β₃/n³
```

| 유의수준 | β∞ (N→∞) | β₁ | β₂ | β₃ |
|---|---:|---:|---:|---:|
| 1% | −3.43035 | −6.5393 | −16.786 | −79.433 |
| 5% | −2.86154 | −2.8903 | −4.234 | −40.040 |
| 10% | −2.56677 | −1.5384 | −2.809 | 0.000 |

**p값을 내지 않는다** (N28). 1%·5%·10% 임계값과의 비교로만 판정한다. 임계값 자체가 하드코딩 근사인데 p값을 소수점으로 내면 **없는 정밀도를 흉내 내게** 된다. 이 사실은 상수 `LIMITATION` 문장으로 응답과 리포트 `limitation` 에 그대로 실린다.

시차 상한은 Schwert(1989) — `⌊12·(n/100)^(1/4)⌋`.

**근거 노트**: N28

### 4.3 ARIMA — Hannan-Rissanen 2단계

MLE(`scipy.optimize`)를 못 쓰므로 OLS 두 번으로 대체한다.

```
1단계  고차 AR(k) 적합 (k ≈ ln(n)²) → 잔차 ê 추정
2단계  y_t 를 [y_{t-1..t-p}, ê_{t-1..t-q}] 에 OLS 회귀 → (φ, θ) 추정
3단계  잔차 백색잡음성 검사 (Ljung-Box) → 실패 시 차수 재탐색
```

**근사인 쪽과 정확한 쪽을 갈라 밝힌다** (N29).

| 계산 | 방법 | 성격 |
|---|---|---|
| Ljung-Box p값 (카이제곱 상측확률) | **Wilson–Hilferty 근사** | 자유도 3 이상에서 오차 0.001 미만 — 닫힌 식이 없다 |
| 정규분포 CDF | `math.erf` | **정확** |
| 정규분포 분위수 | 이분법 | **정확** |

MLE 보다 효율이 낮다. 그래서 **항상 확률보행과 백테스트로 비교하고, 못 이기면 리포트에 그대로 적는다** (기획서 D6).

**근거 노트**: N29

  빠진다 (신규 상장·거래정지 등). H03 이 `G-DATA` Gap 으로 그 사실을 밝힌다.
- **지표가 5종 다 붙지는 않는다.** `per` 는 32건뿐이다 — 적자이거나 스냅샷에 PER 이
  없는 종목은 **비운 채로 둔다** (0 으로 채우지 않는다 · 불변원칙 §2-1).

산업 계열이 322건인 것은 추적성 때문이다. 종목별로 발급해야 되짚을 수 있다. 팩이 CORP-R(최대 121.7KB)보다 크고 왕복 합계도 **IND-R 2,526.6KB · IND-TP 2,696.3KB** 로 늘었으나 Vercel 요청 상한(4.5MB) 안이다. (H04 의 파생 9건이 더해져 IND-R 최종 D- 는 331건이 된다 — §5.8 ⑤)

**H04 — CALC- 의 입력을 팩에서 찾아 문다** (N76 · M7)

M6 까지 H04 가 CALC- 입력으로 `result["data_ids"]` 를 넘기고 있었다. 그런데 **D- 는 H03 이 발급하므로 그 목록은 H04 에서 늘 빈 배열**이었다. 그래서 CALC- 가 전부 입력 없는 계산이었고 드릴다운이 "입력 D- 가 기록되지 않았다"를 띄우고 있었다.

이제 `ledger.find_data` · `ledger.ids_for` 로 팩에서 찾아 문다. **실측 CALC- 입력 채움률 0% → 100%** (CORP-R).

**H05 — `data_ids` 를 채우고, 못 채우면 빈 채로 둔다** (N78 · M7)

차트가 어느 D- 를 그리는지 밝히지 않으면 **장↔데이터 연결의 두 번째 축이 죽는다** (실측 M6 기준 CORP-R 1/4 · CORP-TP 1/6 · IND-R 0/4 · IND-TP 0/2). 못 채우는 자리는 **넷**이다 — 공시 타임라인 · 사업보고서 부문 · 민감도 · **산업 계열의 "업종 주가는 어떻게 움직였나?"**(`stages.py:1491-1495` 가 `data_ids=[]` 로 발급한다). 이것들은 **빈 채로 둔다** — 아무 D- 나 넣으면 차트가 안 쓰는 근거를 댄 것이 된다.

### 5.4.1 피어·산업 선정 (신설)

**① '업종'은 DART 표준산업분류다** (N32)

스냅샷의 `sector` 는 업종이 아니었다 (§2.3 ②). 그 상태로는 "업종 기준" 자체가 불가능했다. 그래서 `data/industry_map.json`(§2.4)을 만들어 `industry_store` 가 읽는다.

**② 접두어를 5→4→3→2자리로 넓혀 가며 맞춘다** (N33)

```
industry_store.peers_by_industry(code, min_peers=5)
  5자리 완전일치 → 부족하면 4자리 → 3자리 → 2자리
```

코드 자릿수가 섞여 있기 때문이다 (3자리 1,378 · 4자리 478 · 5자리 2,025). **완전일치만 보면 삼성전자(264)와 SK하이닉스(2612)가 남남이 된다.** 몇 자리에서 맞췄는지는 응답에 밝힌다.

**③ 시총 밴드는 ±50% 가 아니라 0.5~2.0배** (N34)

시총은 로그 분포다. ±50% 로 자르면 큰 회사 쪽이 지나치게 좁아 피어가 3곳도 안 남는다.

> v1.0 §7.3 질문 카드 그림에 `시총 기준 — 시총 ±50% 밴드`라고 적혀 있었다. **§7.3 문구도 함께 고쳤다.**

**④ 산업 이름표** — §2.4 의 `KSIC_SECTIONS`(21) · `KSIC_DIVISIONS`(74) · `KSIC_GROUPS`(53). 소분류는 **실제 구성 종목으로 대조 확인한 것만** 넣고 나머지는 중분류 이름으로 올린다 (N52).

**⑤ 산업 대상 해석** — `GET /api/research/industries/resolve` 가 산업명 · 업종코드 · **종목명**을 받아 업종으로 바꾼다. `/api/research/industries` 는 `digits`(2~5)로 묶은 목록을 주되, 구성 종목이 적은 산업도 **빼지 않고** `enough` 로 표시만 한다 — 빼 버리면 "왜 내 업종이 목록에 없나"를 설명할 수 없다.

**근거 노트**: N32 · N33 · N34 · N52 · N53

| `저평가 주장` | 피어 대비 성장률·마진 차이 확인 → 차이가 크면 "디스카운트에 이유가 있음" 반증 제시 |
| `추세 주장` | 확률보행 귀무가설 대비 유의성 · 백테스트 적중률 |
| `실적 개선 주장` | 일회성 항목 · 회계기준 변경 · 기저효과 · 현금전환 확인 |
| `상관→인과 검사` | 상관 주장마다 경쟁 가설 최소 1개 + 중간 KPI 요구 (계약 §12.1 "분석 논리" 15점) |

**② 산업 계열** (`stages._industry_red_team`) — 신설

`redteam.run_all` 은 **기업 재무를 전제로 만든 검사**다. 산업에 그대로 들이대면 다섯 개가 전부 '판정불가'로 나와 아무것도 검사하지 않은 것과 같아진다. 그래서 따로 만들었다 (N54).

| 검사 이름 | 무엇을 보나 |
|---|---|
| `시장 규모 주장` | 시장 규모를 실제로 냈는가 — 못 냈으면 `G-SCOPE` |
| `점유율 주장` | 집중도(CR3·HHI)를 냈는가 — 못 냈으면 `G-DATA` |
| `사이클 주장` | 국면 판정의 근거가 있는가 · 판정과 데이터가 어긋나지 않는가 |
| `수요→주가 인과` | 생산지수와 주가를 나란히 놓았는가 · 방향이 어긋나지 않는가 |
| `후보군 완전성` | 상위 몇 곳만 보고 산업 전체를 말하지 않았는가 — 업종 상장사를 전수로 봤으면 `통과` |

**③ 판정불가를 통과로 세지 않는다** (N39 → N73)

"못 본 것"과 "봤는데 괜찮은 것"은 다르다. 실측에서 **매출 성장 검사는 늘 판정불가**다 — 공개 API 에 환율 기여·물량/가격 분해가 없다.

M6 까지 이 원칙은 `confidence` 에만 걸려 있었다. **M7 에서 점수에도 건다** — H10 Red Team 5점 중 2점이 `(통과+실패)/전체` 비율이다 (§5.7). `통과 0 · 실패 1 · 판정불가 4` 는 더 이상 만점이 아니다.

**④ 실패의 처리** — 실패 1건당 해당 주장의 `confidence` 를 한 단계 내리고, 코드가 있으면 `owner="RED"` 인 Gap 을 발행한다. 실패가 하나라도 있으면 `evaluation.verdict` 가 `conditional-pass` 로 내려간다.

**근거 노트**: N39 · N54 · N73

### 5.7 평가 루브릭 — H10 (신설)

> v1.0 §5.1 은 H10 을 "100점 루브릭 채점 · 회귀검사" 한 줄로만 적었다. **9축과 배점이 명세에 전혀 없었다.** 여기서 못박는다.

**① M6 의 문제 — 변별력이 0 이었다** (N71)

화면에 100점을 띄우면서 알게 됐다. **네 작업이 전부 100/100 A** 였다.

아홉 축 **전부**가 "있으면 만점"이었던 것은 아니다. M6 코드(`git show 4c43cd0:app/services/research/stages.py` 의 `h10_evaluate`)를 다시 읽어 보면 —

- **비율로 매긴 축 셋** — 증거 추적성(`cover["data_linked_ratio"]`) · 분석 논리(`len(with_falsify)/len(hypotheses)`) · 해석 품질(`len(full_cards)/len(cards)`)
- **바닥값이 있는 축 둘** — 대상·범위(`1.0 if target.name else 0.3`) · 데이터·계산(`1.0 if calculations else 0.5`)
- **있으면 만점인 축 넷** — 시각화 · Red Team · 사용자 의견 · 양식 (`1.0 if … else 0.0`)

문제는 축의 모양이 아니라 **그 비율들이 M6 에서 전부 1.0 이 나왔다는 것**이다. D- 는 45건이 전부 E- 에 물려 있었고(파생값이 아직 장부에 없었으므로), 가설에는 반증 조건이 다 붙어 있었고, 해석카드도 한계까지 다 채워져 있었다. 그래서 비율 축까지 만점이 되어 총점이 넷 다 100 이 됐다.

| 평가축 | 배점 | 계약이 적은 핵심 검사 | M6 코드가 실제로 잰 것 |
|---|---:|---|---|
| 증거 추적성 | 15 | 핵심 주장→evidence_id→**원문 위치** 연결 | `data_linked_ratio` 하나 |
| 데이터·계산 정합성 | 15 | **단위·통화·기간·기준·식 재계산** | `1.0 if calculations else 0.5` |
| 시각화 정합성 | 10 | 질문·차트 유형·축·**데이터**·출처 일치 | `1.0 if C4_visual else 0.0` |
| 해석 품질 | 20 | 관찰·의미·**인과·대안**·한계·다음 확인 | 한계 한 칸만 |
| Red Team·불확실성 | 5 | **반대 근거와 결론 반전 조건** | `1.0 if checks else 0.0` |

계산 2건이면 만점이고, 검사를 돌리기만 하면 만점이라 IND-TP 가 `통과 0 · 실패 1 · 판정불가 4` 로도 5/5 를 받았다. **그 IND-TP 는 중대 결함 1건을 달고도 총점 100 이었다.**

**② M7 의 결정 — 배점은 손대지 않았다** (N72)

GIC 공통계약 §12.1 을 다시 읽으니 **배점표의 `핵심 검사` 열이 이미 세부 기준을 적어 두고 있었다.** 코드가 그것을 안 재고 있었을 뿐이다. 그래서 **배점 9축 100점은 계약 그대로 두고 축 안의 세부 채점만** 다시 짰다.

**① 출처 등급은 자동 판정한다**

사람이 손으로 고르면 같은 출처가 실행마다 다른 등급을 받게 되고, 그러면 커버리지 평가가 의미를 잃는다.

| 출처 | 등급 | 판정 이유 |
|---|---|---|
| `DART-재무제표` · `DART-사업보고서` | **회사원문** | 회사가 작성해 제출한 원문 |
| `DART-공시목록` · `DART-기업개황` | **1차공식** | 금감원이 접수·관리하는 메타 |
| `KRX` · `ECOS` · `FRED` · `KOSIS` | **1차공식** | 거래소·중앙은행·통계청이 생산 |
| `yfinance` | **2차전문** | 재배포 — **원생산자가 아니다** |
| 그 밖 | 기타 | 등급표에 없는 출처 — 사람이 확인해야 한다 |

**② 파생값을 장부에 올린다** (N69 → N74 · M7)

`ledger.add_derived(pack, metric, value, formula, inputs, …)` 가 **D- 와 CALC- 를 짝으로 발급하고 `(data_id, calc_id)` 를 돌려준다.**

> **파생 D- 에는 `evidence_id` 를 붙이지 않는다.** 입력의 E- 를 물려주면 "주당가치 158,549원의 출처가 DART 재무제표"가 되어 **우리가 만든 값을 남이 발표한 값처럼** 보이게 한다 (불변원칙 §2-1).
>
> 사슬은 끊기지 않는다 — `파생 D- → CALC- → 입력 D- → E-`.

**어디까지 올리나** — 기준은 **리포트 본문에 실제로 실리는 파생값 전수**다. 본문에 안 나오는 중간값을 D- 로 올리면 연결률은 그대로인데 팩만 커진다(그런 것은 CALC- 의 `intermediate` 로 남긴다). 네 리포트의 본문 수치를 전수 분류해 목록을 정했다 — `linkcheck.check_report()` 가 세는 본문 수치는 M7 기준 **네 작업 합계 250개**(CORP-R 79 · CORP-TP 55 · IND-R 40 · IND-TP 76)다.

`add_derived` 호출부는 `stages.py` 의 **네 자리뿐**이다 — 867(`_h04_ind_r`) · 1006·1037(`_h04_ind_tp`) · 1169(`_h04_corp`).

| 올린 것 | 어디 |
|---|---|
| CAGR · 영업이익률 · 순이익률 · ROE · 부채비율 · 유동비율 · 듀폰 3항 · 현금전환 | `_h04_corp` |
| EPS · 피어 중앙값 PER · 주당가치 밴드 3종 · 피어 대비 프리미엄 | `_h04_corp` |
| 상장 시총 합계 · 종목별 시총 비중 · CR3 · HHI | `_h04_ind_r` |
| 후보 시총 비중 · 후보별 coverage | `_h04_ind_tp` |

**값이 없으면 발급하지 않는다.** 위 목록은 코드가 시도하는 전수이고, 실제 발급분은 대상마다 다르다 — 삼성전자 CORP-R 실측 파생 D- 는 **14건**(`revenue_cagr` · `operating_margin` · `roe` · `debt_ratio` · `current_ratio` · `net_margin` · `asset_turnover` · `equity_multiplier` · `peer_median_per` · `eps` · `valuation_band_base/low/high` · `per_premium_pct`)이고 `cash_conversion` 은 값이 없어 빠졌다.

> **생산지수 첫 시점 D- 는 파생값이 아니다.** M7 에 `_h03_industry` 가 신설한 것은 맞으나(`stages.py:656`), KOSIS 가 준 실측치를 `evidence_id` 에 물려 올린 **원자료 D-** 다. `_h03_industry` 에는 `add_derived` 호출이 하나도 없다.

**안 올린 것과 그 이유** — Quick Score 6차원과 IND-TP `adjusted score` 다. 입력이 원시값이 아니라 등급 판정·후보군 안 백분위(0/3/5 앵커)로 **범주화된** 값이라 D- 를 붙여도 되짚었을 때 숫자가 이어지지 않는다. **없는 사슬을 만드는 대신 원천 지표(`r250`·`roe`·`per`·`pbr`·`market_cap`)를 CALC- 의 입력으로만 달았다.**

**③ `coverage()` 는 갈라서 센다** (N75)

| 필드 | 뜻 |
|---|---|
| `data_with_evidence` | **직접근거** — E- 에서 바로 온 원자료 |
| `data_derived` | **계산유래** — 계산이 만든 파생값 (`calc_id` 는 있고 `evidence_id` 는 없다) |
| `data_traceable` / `data_traceable_ratio` | 위 둘의 합 — 어느 쪽이든 되짚을 수 있다 |
| `calculations_with_inputs` / `calc_input_ratio` | 입력 D- 가 기록된 CALC- |
| `data_linked_ratio` | **뜻을 그대로 뒀다** — E- 로 직접 이어진 비율 |
| `by_grade` · `gaps` · `conflicts` | 등급별 E- 수 · Gap · Conflict |

> 합친 숫자 하나만 내면 "123건 전부 근거가 있다"로 읽혀서 **그중 몇 건이 우리가 만든 값이라는 사실이 사라진다.** 기존 `data_linked_ratio` 의 뜻을 바꾸지 않은 것은, 뜻이 조용히 바뀌면 그 값을 읽던 화면·검사가 다른 것을 재게 되기 때문이다.

**④ `trace()` 는 파생 D- 에서 뿌리까지 내려간다**

`D- → 그것을 만든 CALC- → 그 CALC- 의 입력 D- → 각 D- 의 E-` 순으로 펼치고, 파생 D- 는 입력을 타고 내려가 닿는 E- 를 **`root_evidence`** 로 함께 준다 (깊이 4). 이게 없으면 화면이 "E- 가 붙어 있지 않다"만 띄우고 끝나서, 사슬이 실제로는 이어져 있는데도 끊긴 것처럼 보인다.

보조 함수 — `ledger.ids_for(pack, *metrics)` · `ledger.find_data(pack, metric, period)` · `ledger.data_value(pack, data_id)`.

**⑤ 실측** (로컬 · 2026-08-02)

|---|---|---|---|
| CORP-R | 22/45/2/2 → **23/123/14/2** | 10/73 (14%) → **34/79 (43%)** | 100 A → 94.5 A |
| CORP-TP | 22/45/3/2 → **23/119/11/2** | 3/30 (10%) → **10/55 (18%)** | 100 A → 93.0 A |

### 5.9 표기·반올림·연결 판정 규칙 (신설)

**① 금액 표기 — `_trillion()`** (N56)

값이 없으면 **0 으로 채우지 않고** 물결표를 낸다.

```
row.get("revenue", 0)  ← 이걸로는 못 막는다. 키는 있는데 값이 None 인 경우가 있다.
```

**금융업은 '매출액' 계정이 없다.** 신한지주 CORP-TP 의 MD 내보내기가 `None / 1e12` 로 500 이 났던 자리다.

**② 파생값은 원값 그대로 싣고 반올림은 표기하는 쪽에서만 한다**

한 번 실제로 어긋났다 — IND-TP 후보 시총 비중을 `round(x*100, 2)` 로 한 번 더 반올림해 올렸더니 리포트 표기 `99.4%` 와 장부 값 `99.35`(→ 99.3)가 갈려 링크가 안 이어졌다.

**③ 본문 수치 → 장부 연결 판정** (`linkcheck.py` · N67 → N79)

M6 까지 이 규칙은 브라우저(`static/assets/research.js` 의 `linkNumbers`)에만 있었다. M7 에서 H10 이 이 비율을 점수로 재게 되면서(§5.7 축 2) **서버에도 필요해졌다.**

규칙 — **보수적으로, 확실할 때만 링크한다.**

| # | 규칙 |
|---|---|
| 1 | 날짜(`2026-08-02`)와 괄호 안 종목코드(`(000660)`)는 **구간째** 건너뛴다 |
| 2 | 연도(`19xx`·`20xx`)는 수치로 세지 않는다 |
| 3 | 뒤에 개수 단위(`건·개·곳·장·회·차·위·명·종목·년·개월`)가 오면 세지 않는다 |
| 4 | 단위도 소수점도 자릿점도 없는 **세 자리 이하 맨숫자**는 개수·순위로 본다. **예외 — 그 값이 장부에 있으면 센다** (`linkcheck.py:161-163` `… and raw not in index and bare not in index`) |
| 5 | 값이 D- 와 **정확히** 맞고 **같은 줄에 그 지표 이름이 있을 때만** 이었다고 센다 |
| 5-예외 | 지표 이름이 같은 줄에 없어도, **값이 같은 D- 후보가 딱 하나이고 뒤에 값 단위가 붙어 있으면** 잇는다 (`linkcheck.py:176-177` `elif not corroborated and len(candidates) == 1 and _VALUE_SUFFIX.match(after)`). `research.js:652-654` 도 같다 |
| 6 | 값이 같은 D- 가 둘 이상이면 **잇지 않는다** — 아무 D- 나 갖다 붙이면 없는 사슬이 된다 |

값 단위로 인정하는 접미사는 `조·억·%·배·원·점·지수·p·pp` 다.

**지표 이름표(`METRIC_LABELS`)** — D- 의 `metric` 은 영어(`revenue`·`operating_income`·`261.per`)인데 본문은 한국어라 그대로는 못 맞춘다. 본문에 실제로 쓰이는 낱말로 표를 둔다.

```python
"revenue": ["매출"],  "operating_income": ["영업이익"],  "per": ["PER"],
"revenue_cagr": ["CAGR"],  "operating_margin": ["영업이익률"],
"valuation_band_base": ["주당 가치", "주당가치", "기준"],
"cap_share_pct": ["시가총액 비중"],  "cr3_pct": ["CR3"],  "hhi": ["HHI"],
```

**본문 문구를 규칙에 맞춘 자리 하나** (N80) — `export_md` 의 IND-R 경쟁구조 본문을 `{name} {share_pct}%` → **`{name} 시가총액 비중 {share_pct}%`** 로 고쳤다. 점유율이 아니라는 그 장의 요지와도 맞고, 규칙 5(같은 줄에 지표 이름)도 함께 지켜진다.

**④ 자바스크립트와 파이썬의 반올림 차이**

`toFixed()` 는 자바스크립트가 '올림', 파이썬이 '짝수로'라 그대로 옮기면 어긋난다.

```python
# app/services/research/linkcheck.py
Decimal(float(value))  # double 의 정확한 이진값을 잡아
    .quantize(..., rounding=ROUND_HALF_UP)   # ROUND_HALF_UP 으로 자른다
# Math.round 는 math.floor(x + 0.5) 다
```

> ⚠️ **같은 규칙이 두 곳에 있다.** 어긋나면 화면이 보여 주는 연결률과 H10 점수가 달라지고, 그러면 **둘 중 하나는 거짓말이 된다.** 검사 두 겹으로 막는다 (§10).

**근거 노트**: N56 · N67 · N79 · N80

**`GET /api/research/warmup`** (N63)

저장소의 **지연 로딩만** 미리 끝낸다 — `industry_map` · `market_snapshot` · `glossary` 셋. **외부 API 는 부르지 않는다.** 깨우자고 DART·KOSIS 를 두드릴 이유가 없고, 그쪽 응답을 기다리면 워밍업 자체가 느려진다.

```
H00 콜드 5,777ms  →  웜 206ms   (배포본 실측 2026-08-02)
```

응답에 `warm` · `was_cold` · `loaded_now` · `total_ms` · `steps[]`(이름 · ok · `loaded_now` · ms · error)가 온다. 하나가 죽어도 나머지는 깨운다.

> ⚠️ 콜드 여부를 **걸린 시간으로 짐작하지 않는다** — 로컬은 30ms, 배포본은 그보다 느려 어느 문턱을 잡아도 한쪽이 틀린다. 캐시 상태를 직접 본다.
>
> ⚠️ **계층 경계를 넘는 결합이 있다.** `research_router.py:142·144·146` 이 `industry_store._cache` · `snapshot_store._snapshot` · `glossary._cache` 라는 **사설 속성**을 직접 읽는다. 저장소 내부 변수명이 바뀌면 조용히 깨진다. 정리 대상이지만 M7 에서 손대지 않았다.

**M7 재측정 — 기준선을 워크스트림 4종으로 쪼갰다** (`plan.py:88-115`)

M6 은 `corp` / `industry` 둘로 묶었는데, 실측해 보니 **같은 묶음 안에서 H04 가 7~10배 달랐다** — CORP-R 0.61초 vs CORP-TP 2.99초 · IND-R 8.42초 vs IND-TP 0.83초. 묶어 평균 내면 둘 다 틀린 값이 된다. CORP-TP 는 H04 에서 DART 공시목록을 한 번 더 부르고, IND-R 은 H04 에서 밸류체인·사이클을 계산하는데 IND-TP 는 스냅샷만 보고 점수를 매기기 때문이다.

같은 대상을 **다시** 볼 때 (`CACHED_SECONDS` · `plan.py:105-110`) — CORP-R H02 0.21초 · CORP-TP H02 0.20초 · IND-R H02 1.93 · H04 2.28초 · IND-TP H02 1.62초. 전구간으로는 CORP-R 7.8초 · CORP-TP 8.4초 · IND-R 11.5초 · IND-TP 10.2초다.

> **그래도 기준선은 '처음 보는 대상' 쪽으로 잡는다** (`BASELINE["why_first_run"]`). 빠른 쪽을 기준으로 잡으면 처음 오는 사람이 정확히 M6 가 풀려던 문제("왜 멈춰 있지?")를 겪는다. 넘게 예상해 일찍 끝나는 편이 낫다.

**`GET /api/research/glossary`** (N66)

| 모드 | 질의 | 응답 |
|---|---|---|
| 뜻 | `?term=PER` | 그 용어 하나 |
| 검색 | `?q=…` | 앞부분 일치 검색 결과 |

| 색인 | (없음) | 섹션 목록 + 통계 |

리포트에서 용어에 밑줄을 치려면 어느 낱말이 사전에 있는지 알아야 하는데, 사전 전체(185KB)를 내려받을 이유는 없다. 뜻은 마우스를 올린 그 낱말만 `?term=` 으로 받는다. 사전 표기가 `정보 비대칭 (情報 非對稱) / 역선택` 처럼 붙어 있어 화면이 `/` 와 괄호를 떼어 쓰는데, **조각으로 물어도 서버의 앞부분 일치가 찾아 준다.**

**`POST /api/research/export/md`**

응답 — `markdown` · `page_count` · `max_pages`(15) · `merged[]` · `bytes`. H09 가 이미 조립해 팩에 실어 둔 리포트가 있으면 **그것을 쓴다** — 여기서 다시 조립하면 H09 가 본 것과 다른 리포트가 나올 수 있다 (회귀검사 §13 "동기화").

**응답 스키마를 `response_model` 로 조이지 않는다** (N30 과 같은 이유). 그래서 `/docs` · `openapi.json` 에 **리서치 응답 스키마가 비어 있다.** "전 API 가 DTO 로 검증된다"는 서술은 사실이 아니다.

- 기대수익률 · 변동성 · 상관계수는 **실제 KRX 종가**에서 계산한다.
- 난수는 비중 추첨에만 쓰고 **시드가 고정**이라 같은 조건이면 항상 같은 결과가 나온다.
- 종목이 2개 미만이거나 10개 초과면 422.

**① `note` — 요청한 창을 못 채웠으면 밝힌다** (N31)

배포본은 축약본(150거래일)이라 250 을 요청해도 **149일**로 계산된다. 조용히 넘어가면 변동성 숫자를 실제보다 믿게 된다. 그래서 **실제 관측 수와 자료 출처**(`krx_store.source()` 의 `cache`/`bundle`/`live`)를 `note` 에 적는다.

**② `risk_free_source` — 무위험이자율의 출처를 응답에 싣는다** (N48·N58)

§4.6 의 값이 어디서 왔는지(출처 · 기준일 · 교차검증 후보 · 격차)를 함께 준다. `/quant` 화면이 그 문장을 그대로 보여 준다.

> ⚠️ **`response_model` 에 선언하지 않으면 필드가 잘린다.** DTO 가 모르는 필드를 Pydantic 이 버리기 때문에, `FrontierResponse` 에 `risk_free_source` · `note` 를 명시적으로 선언해야 한다. 샤프지수 전체가 이 숫자 하나에 걸려 있어 **출처를 숨기면 검증할 방법이 없다.**

### 6.8 오류 규약

**기본** — FastAPI `HTTPException(detail=…)`. 다만 그룹마다 **의도적으로 다르다.**

| 그룹 | 규약 | 이유 |
|---|---|---|
| **리서치** | 자료가 없으면 **200 + `status="partial-continue"` + Gap Log**. 4xx 는 요청 자체가 말이 안 될 때만 | "자료가 모자라 못 했다"와 "요청이 틀렸다"는 다른 말이다 (불변원칙 §2-2) |
| **대시보드** | 카드 단위 `ok` / `error` 를 두고 **항상 200** | 카드 하나가 실패해도 나머지를 보여 줘야 한다 (N6) |
| **차트** | **오류를 그대로 올린다.** 단 `overlay` 의 개별 지표 실패만 `errors` 에 모아 200 | 차트 한 장이 주인공이라 실패를 숨기면 빈 화면만 남는다 |
| 그 밖 | 표준 HTTP 상태 코드 | |

**리서치 API 의 4xx 는 셋뿐이다**

| 상태 | 언제 |
|---|---|
| 404 | 모르는 워크스트림 · 모르는 상태 ID |
| 400 | `digits` 가 2~5 밖 · 빈 입력 |
| 422 | Pydantic 입력 검증 (Body 형식) |

**예상 못 한 예외도 200 이다.** `research_router.py:234-243` 이 이를 명시적으로 처리해 `partial-continue` + Gap Log 로 바꾼다.

> ⚠️ **일반적인 REST 에러 표를 그대로 쓰면 실제 동작과 어긋난다.** 리서치는 "500 이 안 나는 것"을 설계 목표로 삼은 API 다.

**근거 노트**: N6 · N42

### 7.4 근거 드릴다운

> **v1.0 의 핵심 문장을 교체한다.**
>
> ~~"리포트의 모든 수치는 `data-evidence-id` 속성을 갖는다."~~
>
> → **값이 D- 와 정확히 맞고 같은 줄에 그 지표 이름이 있을 때만 링크를 건다. 값이 같은 D- 가 둘이면 걸지 않는다. 연도·개수·종목코드는 수치로 세지도 않는다. 그리고 못 이은 수를 화면이 그대로 밝힌다.**
>
> 규칙 전문은 §5.9 ③ 에 있다.

**① 왜 전부를 잇지 못하나** (N67)

D- 는 원시 계정(`revenue` · `operating_income` · `equity` …)인데 본문에 나오는 것은 대부분 **파생값**이었다.

```
주당 가치 범위 158,549~237,823원 (기준 198,186원)   ← 밸류에이션 밴드
피어 대비 +32.4%                                    ← 상대 위치
1위 SK하이닉스 · adjusted 4.6 · coverage 100%       ← 점수
```

**아무 D- 나 갖다 붙이면 없는 근거 사슬을 만들어 내는 것**이라 하지 않는다 (불변원칙 §2-1). M7 에서 파생값을 장부에 올려(§5.8) 연결률을 올렸지만 여전히 100% 가 아니다.

| 작업 | M6 | **M7** |
|---|---|---|
| CORP-R | 10/73 (14%) | **34/79 (43%)** |
| CORP-TP | 3/30 (10%) | **10/55 (18%)** |
| IND-R | 3/40 (8%) | **10/40 (25%)** |
| IND-TP | 0/75 (0%) | **5/76 (7%)** |

**못 이었다는 사실을 숨기는 것이 링크를 못 거는 것보다 나쁘다.** 화면이 "본문 수치 79개 중 34개가 근거로 이어진다. 나머지는 파생값이라 장부에 D- 번호가 없다"를 그대로 적는다.

**② 서버 왕복이 없다** (N68)

`ledger.trace()` 와 **같은 규칙을 화면이 그대로 밟는다.** 서버 무상태 설계(§1.3)의 부수 효과다 — 팩에 C1·C2·logs 가 다 실려 있어 서버에 다시 물을 것이 없다. IND-* 의 D- **331건(IND-R) · 328건(IND-TP)** 도 즉시 열린다.

**③ 직접근거와 계산유래를 갈라 밝힌다** (N81 · M7)

| 자리 | 무엇을 보여 주나 |
|---|---|
| 요약 타일 | **"추적가능 N% — 직접근거 X · 계산유래 Y"** |
| 드릴다운 (파생 D-) | "계산으로 만든 파생값이라 직접 근거가 없다. 입력을 따라가면 아래 근거에 닿는다" + `rootEvidence()` 로 E- 를 펼침 |
| 장부 탭 D- 표 '근거' 열 | 파생이면 **`파생 · CALC-…`** |

**파생 D- 에 "근거 없는 수치"라고 띄우면 거짓말이 된다.** 사슬은 실제로 이어져 있다.

**④ 사슬의 모양**

아래는 **지어낸 예시가 아니라 실행 결과다.** CORP-R · 005930 · 2026-08-02 · 로컬 서버(8000)로 12상태를 돌려 받은 팩(E 23 / D 123 / CALC 14)에 `ledger.trace(pack, "D-CORP-R-0120")` 를 그대로 걸어 얻은 값이다.

```

├ 계산  CALC-CORP-R-0011 : 주당가치(기준) = 피어 중앙값 PER × EPS
```

**왜 필요했나** — 배포본에 원본 캐시(123MB)를 못 올려 **`/quant` 4종 · `/krx` 캔들 · `/market` 시장의 폭이 전부 죽어 있었다.** 사용자가 "차트가 안 나온다 · KRX 캐시가 비었다"로 신고한 바로 그 문제다 (N22).

| 산출물 | 내용 | git | 배포 |
|---|---|---|---|
| `data/krx_bundle.db` | 전종목 **150거래일** SQLite · 30MB | **제외** | **포함** |
| `data/krx_derived.json` | 거래일 캘린더 282일 + 시장의 폭 · 13KB | 포함 | 포함 |

빌드 스크립트 — **`python3 scripts/build_krx_bundle.py`**

> ### ⚠️ 배포 전 필수 절차
> **배포 전에 `scripts/build_krx_bundle.py` 를 돌리지 않으면 배포본에서 `/quant` 4종과 `/krx` 캔들이 조용히 죽는다.** `krx_bundle.db` 는 git 에 없으므로 **로컬에서 만든 것이 그대로 번들에 올라간다.** 오래된 번들을 올리면 오래된 데이터가 나가고, 없으면 화면이 빈다.

**왜 150거래일인가** (U-신규 결정 · M3) — 기간을 줄이는 쪽을 택하고 **종목은 자르지 않았다.** 스크리닝 깔때기의 첫 단계가 "전체 상장 종목"이라 상위 N개로 자르면 그 화면의 존재 이유가 사라진다. `/quant` 세 API 는 전부 60거래일, `/krx` 캔들은 120거래일 기준이라 150이면 손실이 없다.

| 후보 | 크기 | 판단 |
|---|---|---|
| JSON gz (전종목 5필드) | 12.9MB | ❌ 콜드스타트마다 풀어 파싱해야 한다 |
| SQLite 전종목 250일 | 48.8MB | 무겁다 |
| **SQLite 전종목 150일** | **30MB** | ✅ 읽기 전용으로 열어 실측 0ms |
| 상위 500종목 250일 | 9.1MB | ❌ 깔때기가 무의미해진다 |

**읽기 규칙** (N24)

```
축약본은 mode=ro 로 연다.
PRAGMA journal_mode=WAL 을 하지 않는다.
CREATE TABLE 을 하지 않는다.
```

배포 번들은 읽기 전용이라 둘 다 **그 자리에서 예외**가 난다.

**저장소가 갈라지는 규칙**은 §1.1 ① 과 같다 — `krx_store` 가 원본이 비면 축약본으로 넘어가고 `source()` 가 `cache`/`bundle`/`live` 를 밝힌다.

**원본 캐시의 쓰기 폴백** — `krx_store.py:58` 이 `PROJECT_ROOT/data/krx_cache.db` 를 보되, 쓸 수 없으면 `krx_store.py:68` 이 `tempfile.gettempdir()/krx_cache.db` 로 떨어진다. **Vercel 은 파일시스템이 읽기 전용이라 늘 이쪽으로 간다** — 그래서 `/tmp` 의 **빈 DB** 가 잡힌다 (§8.5).

**근거 노트**: N22 · N23 · N24

**`POST /api/krx/sync` 가 배포본에서 무의미한 이유** — Vercel 파일시스템이 읽기 전용이라 `krx_store` 가 `/tmp` 의 **빈 DB** 로 폴백한다(`krx_store.py:46` 주석 · 65-68). 거기에 써 봐야 인스턴스가 사라지면 함께 사라지고, 다른 인스턴스는 보지도 못한다. 코드에 '동작하는 수집 API' 로 남아 있으니 **문서에서 배포본 동작을 단언하지 않는다.**

**서버리스 감지는 한 곳뿐이다**

```python
# app/services/research/stages.py:287
return bool(os.environ.get("VERCEL") or os.environ.get("VERCEL_ENV"))
```

여기서만 환경을 본다 (H02 의 원문 읽기 허용 판정). **다른 계층은 환경을 보지 않고 예외/OSError 로 폴백한다** (`krx_store` → `/tmp` · `tmp_cache`). "배포 환경을 감지해 동작을 바꾼다"고 일반화하면 **과장**이다.

### 10.1 `regress_ui.js`

M1 이전 원본(`실습/pages/*.html`)과 지금 화면(`static/pages/*.html`)을 **jsdom 으로 열어 대조**한다. 셸(`shell.js`)을 건드렸으므로 모든 화면이 영향을 받는다.

| 절 | 보는 것 |
|---|---|
| 1 | 각 화면의 핵심 요소 `id` 가 그대로 있는가 (원본에 있던 것이 사라지지 않았는가) |
| 2 | 페이지 스크립트가 문법 오류 없이 파싱되는가 |
| 3 | 셸이 사이드바·티커바를 그리는가 (새 메뉴 포함) |
| **4** | **리서치 화면이 12상태를 끝까지 돌고 리포트를 그리는가** (N70) |
| **5** | **링크 보수성** — 연도·개수·종목코드를 수치로 세지 않는가 (N70) |
| **6** | **서버 링크 규칙과 브라우저 링크 규칙이 같은가** (N79) |

**4절은 서버 없이 돈다.** `fetch` 를 가짜 응답으로 갈아 끼우고 `Research.boot()` 를 **실제로 실행한다** — 실행 드라이버 · 진행률 모달 · 질문 카드 · 드릴다운 · MD 가 한 번에 걸린다.

확인하는 항목 예 — `12상태가 모달에 그려짐` · `12상태 전부 실행됨` · `진행률 100% 도달(가중치 누적)` · **`진행률이 12등분이 아님 (H02 후 27%)`** · `답변이 C6 로 갈 feedback 으로 만들어짐` · `첫 실행은 서버 기준선을 쓴다` · `잰 값이 쌓이면 그쪽을 쓴다`.

**M1 에서 의도적으로 없앤 요소는 회귀로 세지 않는다** — `nav`(예전 상단 가로 메뉴). 여기 적지 않은 누락은 **전부 진짜 회귀**로 본다.

**5절이 못박는 것** — "연도·개수·종목코드를 수치로 세지 않는다"까지 검사해 **정직한 숫자가 오히려 사람을 오해시키는 일**을 막는다.

**6절 — 두 벌 규칙 대조** (N79)

`app/services/research/linkcheck.py` 를 `spawnSync` 로 직접 불러, 같은 리포트·같은 팩을 양쪽에 넣고 `(total, linked, data_ids)` 세 값이 **모두 같은지** 줄 단위로 본다. 규칙의 모든 갈래를 건드리는 **15줄**을 준비해 둔다.

> ⚠️ **파이썬 쪽을 못 돌리면 초록불로 세지 않고 실패로 센다.** 대조를 건너뛴 채 통과하면 어긋남을 놓친 것과 같기 때문이다.

**한 번 실제로 어긋났다** — §5.9 ② 의 반올림 사례가 이 검사에서 잡혔다.

**`render_charts.js`** — **진짜 ApexCharts** 로 그려 본다. 왜 필요했나:

> `regress_ui.js` 는 문법만 보고, `render_timeseries.js` 는 ApexCharts 를 대역으로 바꿔 돌린다. 그래서 **"옵션을 잘못 줘서 차트가 통째로 안 그려지는" 오류가 두 검사 모두를 통과해 배포까지 갔다.** 실제로 배포본 `/market` 에서 두 건이 그랬다.
