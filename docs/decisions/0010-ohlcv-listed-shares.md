# ADR-DS-0010: `ohlcv` 에 `listed_shares` 를 되살린다 — 역산되더라도 원본을 싣는다

## 상태

채택됨 (2026-08-22)

## 맥락

ADR-DS-0002 의 목표 DDL 은 `securities` 에 `listed_shares bigint` 를 두고 `ohlcv` 에서는
뺐다. 종목의 **속성**이므로 종목 표에 한 번만 있으면 된다는 정리였다.

그런데 원본은 그렇게 생기지 않았다. SQLite `daily_price` 는 `listed_shares` 를
**(종목, 날짜)마다** 싣는다. 그리고 `scripts/check_migration_fitness.py` 가 그 값이
기간 안에서 실제로 움직이는 것을 셌다.

    listed_shares 가 변하는 종목    1,256 / 2,870   (43.8%)

절반 가까이가 변한다. 액면분할·병합·유상증자가 이 기간에 흔했다는 뜻이다.
표를 종목당 한 줄로 접으면 **과거의 주식수가 최신 값으로 덮인다.**

지금 그 값을 쓰는 곳은 회전율 한 군데다.

    app/services/market_data.py:109
    "turnover": round(avg_volume / listed * 100, 3) if listed else 0.0

`listed` 가 비면 예외가 아니라 **`0.0`** 이다. 컬럼을 그냥 빼면 화면의 회전율이
전 종목 0.0 으로 조용히 바뀌고, 숫자가 나오기 때문에 아무도 눈치채지 못한다.

## 결정

`ohlcv` 에 `listed_shares bigint` 를 되살린다. `securities.listed_shares` 는
**최신 상태를 나타내는 용도로 그대로 둔다** — 둘은 역할이 다르다.

    securities.listed_shares   지금 이 종목의 주식수 (종목 목록·검색이 쓴다)
    ohlcv.listed_shares        그 거래일의 주식수 (시점 정확도가 필요한 계산이 쓴다)

## 근거

### 접는 안은 10배 틀린다

최신 주식수로 과거 회전율을 계산했을 때의 오차를 실측했다.

| 종목 | 과거 주식수 | 최신 | 회전율 오차 |
|---|---|---|---|
| 134380 미원화학 | 2,199,268 | 21,992,680 | **10.0배** |
| 058430 포스코스틸리온 | 6,000,000 | 60,000,000 | **10.0배** |
| 001130 대한제분 | 1,690,000 | 16,900,000 | **10.0배** |
| 001080 만호제강 | 4,150,000 | 41,500,000 | **10.0배** |
| 290560 신시웨이 | 3,727,122 | 22,362,730 | 6.0배 |

액면분할 10:1 이다. 분할 전 회전율이 10분의 1로 찍힌다. 이 안은 탈락이다.

### 역산은 오늘 기준 정확하지만, 그것이 이유가 되지 못한다

세 번째 안이 있었다 — 저장하지 않고 `market_cap / close` 로 읽을 때 되돌리는 것이다.
780,484행 전부에서 재 봤다.

    market_cap = close × listed_shares      780,484 / 780,484   (100.0000% 정확 일치)
    close 가 0 이거나 NULL 인 행            0
    listed_shares 가 0 이거나 NULL 인 행    0

오차가 없다. 6MB 를 아낄 수 있다. 그런데도 저장을 고른다.

**바로 옆 컬럼에서 이 레포가 이미 같은 판단을 했다.** `ohlcv.change` 주석이 그것이다 —
"close 차이로 역산하면 3원씩 어긋나는 종목이 있어 원본을 그대로 받는다". 그때는 역산이
어긋나는 것을 보고 원본을 골랐고, 지금은 역산이 맞는다. 하지만 **오늘 맞는 것과 앞으로도
맞는 것은 다르다.** 항등식이 깨지는 날 역산은 예외를 던지지 않고 **그럴듯하게 틀린 값**을
낸다. 회전율은 백분율이라 두 배쯤 틀려도 화면에서 이상해 보이지 않는다.

`close = 0` 을 배제할 수 없다는 근거도 실측에 있다. 같은 원본이 **open·high·low 에 0 을
실제로 내보낸다** — 31,153행 · 535종목. close 만 아직 안 겪었을 뿐이고, 겪는 날
`market_cap / close` 는 0 으로 나눈다.

6.0MB(bigint 8바이트 × 780,484행)는 이 표에서 십수 퍼센트다. 시점 정확도를 원본 그대로
보존하는 값으로는 싸다.

### 항등식은 버리지 않고 계속 잰다

역산을 안 쓰기로 했다고 항등식이 쓸모없어지는 것은 아니다. 그것이 깨지는 순간은
**원본의 성격이 바뀌었다는 신호**다(유동주식수로 정의가 바뀌었다든가). 그래서
`check_migration_fitness.py` 가 매 실행마다 이 항등식을 세고, 어긋난 행이 나오면 알린다.
막지는 않는다 — 적재를 멈출 일이 아니라 사람이 봐야 할 일이다.

`CHECK` 제약으로 걸지 않는 이유도 같다. 제약을 걸면 정의가 바뀐 첫 행에서 **배치가
롤백된다.** ADR-DS-0002 를 앞두고 S1 이 통째로 막으려던 바로 그 사고다.

## 결과

- `sql/init/01-schema.sql` 의 `ohlcv` 에 `listed_shares bigint` 가 선다.
- `market_data.py:109` 의 회전율이 **거래일 시점 주식수**로 계산된다. 전환 후에도
  지금과 같은 값이 나와야 한다 — 다르면 적재 쪽을 의심한다.
- 하류 `label-service` 가 시점 정확한 주식수를 쓸 수 있다. 백테스트에서 액면분할 종목의
  회전율·유동성 지표가 분할 시점에 튀지 않는다.
- `tests/test_schema_fitness.py` 가 이 컬럼이 다시 빠지는 것을 막는다.
- 저장 6MB 증가. 파티션마다 나뉘므로 한 파티션당 부담은 그보다 작다.
- ⚠️ **`securities.listed_shares` 와 값이 갈릴 수 있다.** 갈리는 것이 정상이다 —
  한쪽은 최신, 한쪽은 시점이다. 두 값을 비교해 "동기화가 깨졌다"고 읽지 않는다.

## 참조

- ADR-DS-0002 — 파일 캐시를 Postgres 로 옮기되 수집 대장은 그대로 살린다
- `scripts/check_migration_fitness.py` — 위 실측을 매번 다시 재는 자
- `app/services/market_data.py:94·109` — 회전율 계산
- `sql/init/01-schema.sql` — `ohlcv.change` 주석 (같은 판단의 선례)
