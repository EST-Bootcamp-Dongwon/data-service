# ADR-DS-0018: 로컬 읽기 기본값을 Postgres 로 뒤집는다 (전환 S5)

## 상태

채택됨 (2026-08-25)

## 맥락

ADR-DS-0011 이 저장계층 전환을 아홉 걸음으로 갈랐고, S4(ADR-DS-0015)가 읽기 어댑터
`app/repositories/krx_pg.py` 와 `STORE_BACKEND` 스위치를 세웠다. 그때 기본값을 일부러
`sqlite` 로 두었다 — 어댑터를 세우는 커밋과 기본값을 뒤집는 커밋을 갈라야 "어댑터가
틀렸다"와 "전환이 이르다"가 따로 되돌려지기 때문이다.

이 ADR 이 그 두 번째 커밋이다. **S5 의 완료 조건은 "로컬 화면 10개가 Postgres 로만
돈다"** 이고, 여기서 결정한 것은 그 조건을 채우는 과정에서 드러난 네 가지다.

### S4 가 남긴 빚 — 스위치가 안 닿는 경로가 둘 있었다

`tests/test_krx_pg.py` 가 목록을 얼려 두고 있었다. `krx_store.connect()` 를 열어
`daily_price` 에 생 SQL 을 던지는 곳 둘이다. 스위치를 켜도 **그 둘은 계속 SQLite 를
읽는다.** 두 저장소가 같은 자료를 갖고 있는 동안은 예외도 안 나고 화면도 멀쩡하다.

이 ADR 을 쓰며 둘을 다시 보니 **성질이 서로 달랐다.** 하나는 빚이고 하나는 아니다.

## 결정

### 1. `stock_service` 의 우회를 아홉 번째 이음매로 들인다

`app/services/stock_service.py:144-159` 는 **서빙 경로**다 — 한글 종목명·코드로 종목
하나를 찾는 곳이고, 화면의 검색과 야후 접미사 판별이 그것을 쓴다. 스위치가 안 닿으면
두 저장소가 갈린 날 **그 화면만** 조용히 옛 자료를 본다.

`krx_store.lookup_security()` 를 만들어 여덟이던 이음매를 **아홉**으로 늘렸다.

```text
_cache_is_empty · latest_date · available_dates · snapshot_tiered
series_tiered · window · stats · lookup_security      (tier() 는 첫째를 통해 따라온다)
```

⚠️ **동점 처리에 `ohlcv` 가 필요하다.** SQLite 는 `daily_price` 한 표에 이름과 거래대금이
같이 있어 `ORDER BY bas_dd DESC, value DESC` 가 공짜였다. Postgres 는 이름이 `securities`,
거래대금이 `ohlcv` 라 둘을 이어야 한다. 그 두 줄을 빼고 `securities` 만 보면 **정렬 근거가
사라져** 힙 순서가 나온다 — "삼성" 이 삼성전자가 아니라 삼성공조를 가리키게 되고
**오류는 뜨지 않는다.** `JOIN LATERAL` 로 종목마다 최근 한 줄만 보아 파티션 프루닝을
살렸다(S4 머리말의 "`security_id` 를 먼저 푼다" 와 같은 모양).

`tests/test_krx_pg.py` 가 그 세 조각(`ohlcv` · 정렬 · `NOT is_delisted`)이 SQL 에 남아
있는지 검사한다. 조용히 틀리는 고장이라 검사가 문장을 붙들고 있어야 한다.

### 2. `build_stock_master.py` 의 우회는 **빚이 아니다. 그대로 둔다**

갱신 사슬(`refresh_job.STEPS`)에서 이 스크립트는 **4단계**이고 Postgres 적재
(`load_pg.py`)는 **5단계**다. 그 시점에 Postgres 에는 이번 회차 자료가 아직 없다.
뒤집으면 **직전 회차** 자료로 마스터를 만든다 — 24거래일 밀린 날이면 24일치가 틀린다.

결정적인 것은 `--skip-pg` 다. 그 플래그는 `needs_db=True` 인 단계만 건너뛰므로,
2~4단계가 Postgres 를 읽으면 **DB 없이 도는 갱신이 통째로 깨진다.** `--skip-pg` 는
없어도 되는 편의가 아니라 "DB 를 안 띄운 기계에서도 자료를 따라잡는다"는 계약이다.

⇒ 이 우회는 **S8(쓰기 경로 전환)이 SQLite 를 없앨 때 자연히 사라진다.** 그전까지는 옳다.
검사의 주석을 "갚아야 할 빚"에서 "사슬 순서상 의도된 것"으로 고쳐 적었고, 스크립트
본문에도 근거를 남겼다 — 안 적으면 다음 사람이 "고칠" 자리다.

### 3. 기본값은 **환경마다 다르다**

```text
로컬   → postgres    S5 가 뒤집은 값
배포본 → sqlite      아직 DATABASE_URL 이 없다. 그것을 주는 것이 S6(Supabase)
```

⚠️ **한 값으로 뒤집으면 배포본이 죽는다.** 배포본에서 `settings.database_url()` 은
기본값으로 대신하지 않고 **예외를 던진다**(ADR-DS-0003 §2). 거기서 `postgres` 로 읽으면
화면 10개가 그대로 500 이 된다. "로컬만 뒤집는다"는 조심이 아니라 **S5 와 S6 의 경계
그 자체**이고, ADR-DS-0011 의 완료 조건이 처음부터 그렇게 적혀 있었다("**로컬** 화면 10개").

`settings.default_store_backend()` 가 `is_vercel()` 을 보고 고른다. 자동 감지
(`VERCEL`·`VERCEL_ENV`)로 들어와도 같아야 한다 — `APP_ENV` 를 한 번 빠뜨리는 것이
이 레포가 이미 아는 기본 사고 지점이다(ADR-DS-0003 §3). 검사가 세 진입로를 모두 본다.

**되돌리는 단위는 여전히 환경변수 한 줄이다** — `STORE_BACKEND=sqlite`.

### 4. 갱신 사슬은 **쓰기 측(SQLite)에 못 박는다**

이것이 이 걸음에서 가장 값진 발견이다. 기본값을 뒤집자 그 값이 **사슬 자식 프로세스까지
새어 들어갔다.** 다섯 단계가 전부 SQLite 를 다루는데 읽기만 Postgres 로 가는 어긋난
상태가 된다. 실측으로 드러난 두 가지:

| | 무슨 일이 나나 | 위험 |
|---|---|---|
| `fetch_krx.py --status` | `store.stats()` 에서 곧장 죽는다. 자식에게는 기본 `DATABASE_URL` 의 `@db:5432` 가 안 풀린다 | 시끄럽다 — 바로 보인다 |
| `build_market_snapshot.py` | **죽지 않는다.** `krx_store` 읽기 함수를 쓰므로 Postgres 를 읽어 **직전 회차** 자료로 스냅샷을 만든다 | ⚠️ 오류 없이 날짜만 틀린다 |

아래쪽이 훨씬 비싸다. 이 레포는 이미 그 방식으로 24거래일을 잃었다(ADR-DS-0016).

`refresh_job.CHAIN_ENV` 한 표에 `STORE_BACKEND=sqlite` 를 적고, **화면(`_run_step`)과
셸(`tasks.py`)이 같은 표를 읽는다.** 두 벌로 적으면 "화면으로 갱신하면 맞고 셸로 갱신하면
틀리다" 가 되는데, 그 어긋남은 재현이 어렵고 오래 간다 — ADR-DS-0017 이 사슬 정본을
하나로 모은 이유와 같다. `tests/test_refresh_job.py` 가 두 경로 모두를 검사한다.

⚠️ **S8 이 쓰기를 Postgres 로 옮길 때 이 표를 지운다.**

### 5. 접속 실패를 막다른 길로 두지 않는다

기본값이 `postgres` 가 되면서 **"DB 를 안 띄우고 앱을 켠다"가 새 clone 의 첫 경험**이 됐다.
그때까지 화면에 남던 것은 `[Errno 111] Connect call failed` 한 줄이었다 — 원인이
저장소 전환으로 보이지 않는다.

`krx_pg._fetch()` 가 `OSError` 만 잡아 **처방을 붙여 다시 던진다.**

```text
시세 저장소(Postgres)에 못 붙었다: [Errno 111] Connect call failed
  붙는 곳: postgresql+asyncpg://postgres:***@127.0.0.1:1/data_service
  DB 를 띄운다      : docker compose --profile local-db up -d
  호스트 셸이라면   : DATABASE_URL 의 @db:5432 를 @localhost:5432 로 바꾼다
  SQLite 로 되돌린다: STORE_BACKEND=sqlite (S5 이전과 같아진다)
```

⚠️ **삼키는 것이 아니다.** 예외는 그대로 올라간다 — 바꾸는 것은 메시지뿐이다.
빈 결과로 바꾸면 DB 장애가 "그 날짜에 자료 없음"으로 위장돼 화면이 조용히 강등된다
(ADR-DS-0015 가 세운 원칙). `OSError` 만 잡는 것도 그래서다 — 인증 실패·DB 이름 오타는
asyncpg 가 더 정확히 말한다.

### 6. 검사 격리에 한 줄이 더 필요해졌다

`tests/conftest.py` 의 autouse `isolate_env` 는 `STORE_BACKEND` 를 **지우고** 있었다.
S4 까지는 그것으로 충분했다(지우면 `sqlite` 로 떨어졌다). 이제는 지우면 `postgres` 로
떨어지고, 바로 윗줄이 붙을 수 없는 주소를 꽂아 두었으므로 읽기 경로를 타는 검사가
전부 죽는다 — **실측 11건**(`test_source_vocabulary` 전부).

`monkeypatch.setenv("STORE_BACKEND", "sqlite")` 로 **덮어쓴다.** "지우는 것만으로는
부족하다"가 `DATABASE_URL` 에 이어 여기서도 참이 됐다.

⚠️ 그래서 검사 묶음은 새 기본값을 **재현하지 않는다.** 실 DB 가 없어 잴 수 없기 때문이다.
기본값 자체는 `tests/test_krx_pg.py` §3 이 `monkeypatch` 로 환경을 만들어 직접 본다.

## 검증

### 로컬 화면 10개가 Postgres 로만 도는가 — SQLite 파일을 치우고 잰다

이것이 S5 의 완료 조건이고, "**로만**" 을 재는 방법은 하나뿐이다 — `data/krx_cache.db`
(129MB)를 옆으로 치우고 `/tmp` 캐시를 비운 뒤 서버를 다시 띄운다. 축약본
(`krx_bundle.db`)은 **일부러 남겨 둔다** — 어딘가 폴백했다면 층 표시가 `bundle` 로
드러나야 하기 때문이다.

| | 결과 |
|---|---|
| 화면 10개 (`/` `/dashboard` `/market` `/research` `/krx` `/kosis` `/yf` `/stock` `/quant` `/timeseries`) | **전부 200** |
| 저장소를 타는 API 18경로 | **전부 200** |
| 층 표시 | 전부 `krx-db` · `mode=db` — **`bundle` 로 내려간 경로 0건** |
| `/api/krx/status` | 821,928행 · 297거래일 · 2,875종목 · 20250609~20260824 · `data_service.ohlcv` · 111.9MB |
| 한글 종목명 (`/api/stock/삼성전자`) | `005930` · 삼성전자 — SQLite 없이 해결됐다 |

### 두 저장소가 같은 답을 내는가 — `lookup_security` 20건

입력 20개(코드 3 · 정확이름 6 · 접두이름 7 · 없는 이름 2 · 공백 포함 2)를 두 백엔드에
같이 넣었다. **20/20 일치.**

같은 표에서 응답시간도 나왔는데 차이가 컸다.

| | SQLite | Postgres |
|---|---|---|
| 코드 조회 | 87~106ms | 2~4ms |
| **이름 조회** | **3,000~7,600ms** | **2~7ms** |

`daily_price` 에 `name` 인덱스가 없어 821,928행을 전부 훑는다. 자동완성이 이 경로를
쓰지는 않지만(마스터 JSON 을 쓴다), `/api/stock/<한글이름>` 은 이 경로다.

### 동시 48 요청 — 다리의 루프가 하나인 것이 문제가 되는가

ADR-DS-0015 가 남긴 숙제다. 전용 배경 루프 하나로 조회가 직렬화되므로, 화면 열이 동시에
그것을 쓰는 첫 순간이 S5 라고 적어 두었다. 무거운 경로 4종을 48 동시 요청으로 잰다.

| | 성공 | 전체 소요 | 응답 중앙값 |
|---|---|---|---|
| **Postgres** | **48/48** | **8.9초** | 7,654ms |
| SQLite | 24/48 | 121.3초 | 120,095ms (절반이 120초 타임아웃) |

**직렬화는 실재하지만 SQLite 보다 13.6배 빠르다.** 그리고 SQLite 는 절반이 실패한다 —
`init_db()` 가 조회마다 전역 자물쇠와 쓰기를 하는 탓이다(S4 가 지목한 것). 중앙값이
7.6초인 것은 48개가 줄을 서기 때문이고, 실제 사용(화면 열 남짓)에서는 위 표의
개별 응답시간이 답이다. **루프를 늘리는 것은 지금 필요하지 않다** — 필요해지면 그때
잰다. 근거 없이 늘리면 커넥션 전략(ADR-DS-0003 rev.2)을 다시 재야 한다.

### 갱신 사슬 — 두 실행처 모두

| | 결과 |
|---|---|
| `invoke refresh --check` | 5단계 전부 통과 · 적재 대조 21항목 일치 · 요약 `db · 20260824 · 297거래일 · 821,928행` |
| `POST /api/refresh/run {"check":true}` | `state: done` · 같은 결과 |

`invoke check` 초록 — **275 tests** (S4 의 263 에서 12 늘었다).

## 기각한 대안

**① 기본값을 한 값으로 뒤집고 Vercel 환경변수에 `STORE_BACKEND=sqlite` 를 넣는다.**
설정이 코드 밖으로 나가서, 그 변수를 지우는 순간 배포본이 죽는다. 그리고 그 사실이
레포 어디에도 안 적힌다. 환경마다 다른 기본값은 이 레포가 `APP_ENV` 로 이미 쓰고 있는
모양이다(ADR-DS-0003) — 같은 자리에 같은 모양으로 둔다.

**② `build_stock_master.py` 도 Postgres 로 옮기고 `load_pg.py` 를 4단계 앞으로 당긴다.**
저장소가 하나로 모이는 것처럼 보이지만 `--skip-pg` 가 깨진다. DB 를 안 띄운 기계에서
자료를 따라잡는 길이 사라진다.

**③ `stock_service` 가 기존 이음매(`snapshot`·`window`)를 조합해 이름을 찾는다.**
새 이음매가 안 늘지만 전 종목을 가져와 걸러야 해서 느리고, SQL 의 `ORDER BY` 가 담고
있던 "거래대금 큰 쪽" 이라는 뜻이 파이썬 쪽으로 흩어진다.

**④ 접속 실패를 빈 결과로 바꿔 축약본으로 내려간다.** DB 장애가 "자료 없음" 으로 위장돼
화면이 조용히 강등된다. ADR-DS-0015 가 명시적으로 금지한 것이다.

## 결과

- 로컬 읽기 경로가 Postgres 다. `STORE_BACKEND=sqlite` 한 줄로 되돌아간다
- 배포본은 그대로 SQLite/축약본이다. 그것을 푸는 것은 **S6**(Supabase)
- 쓰기 경로는 여전히 SQLite다 — **S8**. 그래서 갱신 사슬이 그쪽에 못 박혀 있다
- 읽기 표면을 우회하는 곳이 둘 → **하나**로 줄었고, 남은 하나는 의도된 것이다

### 남는 숙제

- **낱말이 아직 낡았다** — `tier` 는 `db` 그대로이고 화면 두 곳이 그 값을 정확비교한다.
  대시보드 카드는 "원본 캐시" 를 "원본 저장소" 로 고치고 `db_path` 를 함께 밝히는 데까지만
  했다. 어휘 정리는 **S7** 이다
- **`krx_bundle` 이 아직 사다리에 있다.** 폐기는 배포본이 DB 를 읽은 뒤(S6)에만 한다
- **다리의 단일 루프**는 그대로다. 48 동시에서 견디지만 직렬화는 실재한다
- `krx_store` 의 `init_db()` 가 SQLite 경로에서 조회마다 불리는 것도 그대로다.
  Postgres 경로는 분기가 그 앞에 있어 안 탄다
