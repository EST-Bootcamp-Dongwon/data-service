# ADR-DS-0016: 갱신 사슬을 `invoke refresh` 한 명령으로 묶고, 검증에는 묶지 않는다

## 상태

채택됨 (2026-08-25)

## 맥락

배포본 대시보드의 **데이터 상태** 카드 두 장이 동시에 나빠 보였다.

| 카드 | 배지 | 실제 원인 |
|---|---|---|
| 시장 스냅샷 | `17거래일 전` (기준일 2026-07-31) | **자료가 낡았다** — 24일 동안 아무도 갱신하지 않았다 |
| KRX 시세 | `라이브 조회` | **저장소가 배포본에 없다** — 낡음과 무관하다 |

둘이 같은 자리에 나란히 떠서 하나의 고장처럼 보이지만 **원인도 처방도 다르다.**
아래는 그 둘을 갈라 놓은 기록이다.

### ① 시장 스냅샷 — 갱신이 멈춘 이유

자료를 최신 거래일까지 따라잡히는 일은 스크립트 **다섯 개를 순서대로** 돌리는 것이었고,
그 순서는 README 여러 절과 사람 머릿속에만 있었다. 실측한 사슬은 이렇다.

| # | 스크립트 | 산출물 | git | 배포본에 닿나 |
|---|---|---|---|---|
| 1 | `fetch_krx.py` | `data/krx_cache.db` | ❌ | ❌ |
| 2 | `build_krx_bundle.py` | `krx_bundle.db` · `krx_derived.json` | 뒤엣것만 ✅ | 뒤엣것만 |
| 3 | `build_market_snapshot.py` | `market_snapshot.json.gz` | ✅ | ✅ |
| 4 | `build_stock_master.py` | `stock_master.json` | ✅ | ✅ |
| 5 | `load_pg.py` | Postgres `ohlcv` · `securities` | — | S6 이후 |

**순서가 뜻을 가진다** — 2~4 는 전부 `krx_cache.db` 를 읽으므로 수집이 먼저다.
그리고 **1만 돌리면 로컬 화면은 최신인데 배포본은 그대로 낡는다.** 배포본이 읽는 것은
커밋되는 3·4 쪽이기 때문이다. 이 어긋남은 화면에 오류로 뜨지 않고 **날짜로만** 드러난다.

2026-08-01 이후 24일 동안 이 사슬이 한 번도 돌지 않았다. 명령이 하나였다면
"돌렸나 안 돌렸나"가 한 눈에 보였겠지만, 다섯 개였기 때문에 **부분적으로 돌린 것과
아예 안 돌린 것이 구별되지 않았다.**

### ② KRX 시세 — 갱신으로 풀리지 않는 것

배포본에서 이 카드가 `라이브 조회`인 것은 자료가 낡아서가 아니라 **저장소 파일이
배포본에 실리지 않기** 때문이다. `.vercelignore` 가 2026-08-17 에 이미 적어 둔 사실이다 —
GitLab 연동 배포는 **git 에 있는 것만** 올리므로, `.gitignore` 된 `krx_bundle.db`(30MB)는
`.vercelignore` 가 무슨 말을 하든 배포본에 닿지 않는다.

그런데 그 카드의 안내문은 `python3 scripts/build_krx_bundle.py` 를 돌리라고 말하고 있었다.
**배포본을 보는 사람에게는 따를 수 없는 처방**이다 — 돌려도 배지가 그대로라서
"명령이 고장났나"로 시간을 버린다.

## 결정

### 1. 갱신 사슬을 `invoke refresh` 한 명령으로 묶는다

```bash
invoke refresh                # 최근 30거래일 · 다섯 단계 전부 (약 4분)
invoke refresh --days 250     # 오래 쉬었을 때
invoke refresh --check        # 아무것도 바꾸지 않고 낡음 정도만 잰다
invoke refresh --skip-pg      # 로컬 Postgres 를 안 띄웠을 때
```

- **커밋하지 않는다.** 산출물 셋이 git 에 올라가고 push 가 곧 Vercel 배포다.
  배포 시점은 사람이 정한다. 대신 끝에서 커밋 절차를 한 줄로 다시 알린다.
- **끝에 사람이 실제로 보는 두 숫자를 다시 찍는다** — KRX 최신 거래일, 스냅샷 기준일·낡음.
  단계별 로그는 길어서 마지막 판정이 스크롤 위로 사라진다.
- **5단계는 못 붙으면 건너뛴다.** TCP 로 1초 두드려 보고 안 되면 알리고 넘어간다.
  Postgres 는 아직 읽기 기본값이 아니라(S5 전) 시세 갱신 자체를 막을 이유가 없다.
  다만 **건너뛰면 두 저장소가 갈린다**는 것을 그 자리에서 말한다.
- **`--check` 는 각 스크립트가 이미 가진 확인 모드를 잇는다** (`--status`·`--check`·
  `--verify-only`). 확인 전용 경로를 새로 짜면 그것이 또 갈라진다.

### 2. `invoke check` 에 묶지 않는다

검증 명령이 외부 API 를 부르고 파일을 고치기 시작하면 **그 명령을 더는 신뢰할 수 없다.**
`invoke check` 는 인증키가 없어도 · 네트워크가 없어도 같은 답을 내야 한다.
`invoke hooks` 를 check 에 묶지 않은 것과 같은 이유다 (ADR-DS-0013).

### 3. 실행처는 아직 사람이다

CI 를 필수 경로에 두지 않는 것이 이 레포 방침이다. 스케줄 자동화는 이번에 하지 않는다 —
KRX 인증키를 CI 비밀로 옮겨야 하고, 커밋·양쪽 원격 push 가 자동으로 배포까지 이어지므로
**결정의 크기가 이 문제보다 크다.** 다음 후보는 OS 스케줄러(장 마감 후)이고,
그때 이 ADR 에 덧붙인다.

### 4. 화면의 처방을 환경별로 가른다

`_data_status()` 의 KRX 카드가 `APP_ENV` 를 보고 갈린다.

| 환경 | 처방 |
|---|---|
| 로컬 | "`invoke refresh` 로 수집부터 축약본까지 한 번에 만들 수 있습니다" |
| 배포본 | "git 연동 배포는 축약본을 옮기지 못하므로 다시 만들어도 그대로입니다 — Postgres 전환이 해소합니다 (S6)" |

스냅샷 카드에는 **마지막 생성 시각**을 더했다. 기준일만 보이면 *"자료가 그날까지 있다"* 와
*"그날 이후로 아무도 안 돌렸다"* 가 구별되지 않는다 — 실제로 그 둘을 못 갈라서 24일이 밀렸다.
이쪽 처방은 **배포본에서도 유효하다**(스냅샷은 커밋되므로 로컬에서 만들어 push 하면 닿는다).

### 남는 숙제

- **실행처가 여전히 사람이다.** 명령은 하나가 됐지만 누가 언제 돌리는지는 정하지 않았다.
  같은 일이 다시 밀릴 수 있고, 그때는 카드의 *마지막 생성 시각*이 먼저 드러낸다.
- **배포본 KRX 시세는 이 ADR 이 풀지 않는다.** S6(Supabase) 가 목적지다.
  그전까지 배포본은 `mode=live` · `days=0` 이고 그것은 **회귀가 아니다.**
- **`load_pg.py` 의 마지막 판정문이 낡았다** — "다음은 S4" 라고 말하는데 S4 는 끝났다.
  낱말 정리는 S7 과 함께 한다.
- 오늘(20260825) 은 0건으로 기록됐다. 장 마감 뒤 다시 받으면 채워진다
  (`ZERO_ROW_RETRY_DAYS = 7` 이 최근 0건을 다시 확인한다).
