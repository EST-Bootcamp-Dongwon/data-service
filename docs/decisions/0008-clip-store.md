# ADR-DS-0008: 화면에서 담는 자료를 한 표(`clip`)에 모으고 날짜를 두 축으로 나눈다

## 상태

채택됨 (2026-08-18) — DDL 만 적용. 라우터·화면 구현은 ADR-DS-0002(저장계층 전환) 이후.

## 맥락

화면에서 본 자료를 **화면마다 따로 담아 두고 나중에 찾아보고 싶다**는 요구가 나왔다.
담을 것은 네 종류다 — 뉴스·공시 링크 / 조회한 데이터셋 스냅샷 / 생성한 리서치 리포트 /
내가 쓴 메모·태그. 조회 축으로는 **날짜별 · 월별 · 산업별**이 명시됐다.

지금 상태로는 아무것도 남지 않는다. 서버측 보관은 0건이고, 저장 기능이라곤
`static/assets/research.js` 의 localStorage 하나뿐이라 브라우저를 바꾸면 사라진다.

뉴스 클라이언트도 없다. `scripts/kosis_rss.py` 는 통계 공지 크롤러이지 뉴스가 아니다.

## 결정

1. **한 표 `clip` 에 모은다.** 종류는 `kind` 컬럼으로 구분하고 가변 필드는 `payload`(jsonb).
   → 종류별로 표를 넷 만들면 "이 화면에서 담은 것 전부"를 낼 때마다 UNION 넷이 된다.
     그 질의가 가장 잦으므로 나누지 않는다.
2. **날짜를 두 축으로 나눈다.**
   - `occurred_at` — 자료 자체의 날짜(기사 발행일·공시일·데이터 기준일). **날짜별/월별 묶기용**
   - `saved_at` — 내가 담은 시각
   하나로 합치면 둘 중 하나를 반드시 잃는다.
3. **뉴스 본문은 담지 않는다.** 링크·제목·출처·발행일·내 메모까지다.
4. **산업은 자동 유도 + 수동 보정.** `security_id` 가 있으면 `industry_map` 으로 KSIC 를
   유도하고, 없는 자료(거시 뉴스 등)는 사용자가 고른다. 어느 쪽인지를 `industry_source`
   (`auto`/`manual`)에 남긴다 — **재유도 배치가 사용자 보정을 덮어쓰지 않게 하기 위해서다.**
5. **데이터셋 스냅샷은 조건 + 요약통계까지만.** 값 전체는 담지 않는다.
   `payload = {source, params, summary}` 형태이고 전체 값은 API 재호출로 재현한다.
6. **수집 경로는 둘.** DART 공시 목록(`dart_data.fetch_disclosures` — 이미 있다) ·
   네이버 검색 API(뉴스). 키는 `.key` 의 `NAVER_API_CLIENT_ID`·`NAVER_API_SECRET_KEY`
   에 이미 배치돼 있다(`app/core/secrets.py` 규약).
7. **지금은 DDL 까지만.** 라우터·화면은 저장계층이 Postgres 로 전환된 뒤 붙인다.

## 근거

- **한 표 + `kind`**: 요구의 핵심이 "화면마다 따로 확인"이고 그건 `WHERE screen = ? AND kind = ?`
  한 줄이다. 종류별 필드가 아직 확정되지 않은 단계라 `payload` 로 흘리는 편이 스키마 변경을 줄인다.
- **두 날짜 축**: "8월에 나온 기사"와 "어제 내가 담은 것"은 다른 질문이다.
- **본문 미저장**: 언론사 본문 저장은 저작권 문제가 실재한다. 사용자 요구도
  "링크나 이런 것들을 보관"이었다.
- **`industry_source`**: 자동 유도만 두면 나중에 배치를 돌릴 때 사람이 고친 값이 조용히 되돌아간다.
- **스냅샷 깊이**: 일봉 3천 행을 통째로 담으면 한 건에 수백KB다. 요약통계면 1KB 수준이고
  "그때 뭐가 어땠는지"는 남는다. **대신 수정된 과거 데이터는 그대로 재현되지 않는다** — 감수한다.
- **DDL 먼저**: 스키마를 나중에 박으면 이미 쌓인 행을 전부 다시 채워야 한다.
  `sql/init/` 은 볼륨이 빌 때만 실행되므로 지금 넣어 두는 비용이 0 이다.

## 결과

- `sql/init/03-clip.sql` 이 생겼다. 표 6번째다.
- 요구된 세 축이 인덱스 하나씩으로 받쳐진다 —
  `clip_screen_kind_idx` · `clip_industry_idx` · `clip_security_idx`, 태그는 gin.
- 같은 기사를 두 번 담는 것은 `clip_kind_urlkey_uq` 가 막는다.
  ⚠️ `url_key` 가 NULL 인 행(dataset·report·memo)은 이 제약에 걸리지 않는다 — **의도한 동작**이다.
  같은 조회를 시점을 달리해 여러 번 담을 수 있어야 한다.
- **비용**: `payload` 가 jsonb 라 종류별 필드에 DB 차원의 타입 검증이 없다.
  라우터를 붙일 때 Pydantic 으로 `kind` 별 스키마를 검증해야 한다.
- 네이버 API 는 일일 쿼터가 있다. 수집 배치를 만들 때 호출 수 상한을 함께 둔다.

## 검증 (2026-08-18)

`docker compose --profile local-db up -d` 로 빈 볼륨에서 기동해 확인했다.

- 표·인덱스 7개·CHECK 3개·FK 1개 생성 확인
- 링크형인데 `url` 없음 → `clip_link_needs_url_ck` 가 거부
- 같은 `url_key` 재투입 → `clip_kind_urlkey_uq` 가 거부
- 알 수 없는 `kind` → `clip_kind_ck` 가 거부
- 월별·산업별(`LIKE '26%'`)·화면별×종류별 집계가 의도대로 나옴
- `dataset` 2건은 `url_key` 가 NULL 이라 중복 제약에 걸리지 않음
